# Codex runner isolation, persistence, and settings: initial findings

Status: partial local evidence, 2026-09-29. This publishes corrected probes and
credential-free results for [specs issue #120](https://github.com/amadou-6e/specs/issues/120).
The persistence and stream probes remain unexecuted because no dedicated
Laomedo credential is available. This is not a go decision.

The [Codex Agent component](../components/codex-agent.md) defines the proposed
flow step; [runner isolation](../sandboxing/runner-isolation.md) and
[run traces](../monitoring/run-traces.md) specify shared execution boundaries.
The spike code is at
[`laomedo/experiments/feasibility/120/`](https://github.com/amadou-6e/laomedo/tree/docs/120/experiments/feasibility/120)
and open for review in Laomedo PR [#2](https://github.com/amadou-6e/laomedo/pull/2).

## Relationship to #119

## Protocol notes from the app-server reference

The first probe draft misread the protocol. The corrected probes follow the
[official app-server reference](https://learn.chatgpt.com/docs/app-server):

- Resume uses the dedicated `thread/resume` method with `threadId`;
  `thread/start` has no `threadId` parameter.
- The effective `model`, `reasoningEffort`, `sandbox`, and `approvalPolicy` are
  top-level fields of the `thread/start` result, not fields of the returned
  thread object. The probes read the result level and record which key sets
  were present so a different runner version cannot be misread.
- A `turn/start` response carries no effort field; its `Turn` object holds id,
  items, status, and timing. Per-turn effective effort must come from
  elsewhere, such as the rollout file's `turn_context` record, which is
  outside the current probes' scope and is recorded as unknown here.
- Stream item types are `commandExecution`, `fileChange`, `mcpToolCall`,
  `dynamicToolCall`, and others. There is no `toolCall` or `toolResult` item;
  each item carries its own call and result fields (for example,
  `commandExecution` carries `command`, `aggregatedOutput`, `exitCode`, and
  `status`). A result is counted only when the same item ID has both a started
  event and a terminal completed event with an actual result value.
- Reasoning effort is the typed `turn/start` field `effort`, not a
  `thread/start` config override.
- On the pinned CLI, direct `thread/start` with an unknown model and
  `turn/start` with invalid effort `superultra` were both initially accepted
  without a credential. The runner now validates against `model/list` before
  dispatch. The corrected no-model probe rejected an unknown model, an
  invalid effort, and `gpt-6-luna` with unsupported `ultra` effort locally;
  it sent no `turn/start` and made zero model calls.
- `thread/start`, `thread/resume`, and `thread/fork` return
  `instructionSources`, the loaded instruction-file paths. The isolation probe
  uses this to check for a leaked personal `AGENTS.md`. The returned thread
  also carries `cliVersion`, recorded next to `codex --version` so the version
  that actually served the thread is visible.

## Credential gate

No dedicated Laomedo credential is available. Both credentialed probes stop
before any model call unless the gate passes. The gate requires a declared
secret-store reference and API-key mode, rejects an exact copy of the personal
auth file and any ChatGPT login, and refuses state inside a git working tree.
It checks TCP reachability to `api.openai.com:443` as a prerequisite. The
reference is a declaration by the provisioner; the script cannot prove that
an API key belongs to a dedicated identity. Verify that provenance outside
the probe before running. A dedicated ChatGPT service-account token, which
#119 listed as a production option, is also blocked; that is a conservative
spike choice, not a finding about service accounts.

USD 20 is the cap from issue #120. With an API-key credential the spend is real
provider spend; it is tracked from the provider dashboard plus the recorded
token-usage events, not estimated from a subscription. The paid probes prefer
an advertised `gpt-6-luna` low-effort pair and submit at most three turns
across one execution of each script. A ChatGPT-authenticated run would not be
billed in dollars and is out of scope here.

## Workspace snapshot scope limit

Condition 3 as written in #120 is about resuming from the runner's last
post-run workspace snapshot. Codex does not know about Laomedo snapshots.
The updated probe now requires a completed first turn, copies and hashes the
post-run disposable project, introduces a synthetic drift file, restores the
snapshot, checks the restored hash, and only then calls `thread/resume` after
restarting app-server. A unit test verifies missing-snapshot refusal happens
before changing the project. This tests the guard in the spike, not a
production runner registry. Native restart/resume remains unobserved until a
credentialed run succeeds.

## Remaining: native vs final-response bridge comparison

Analysis only; no remote environment is provisioned or tested. True
remote-only persistence would need a separate host holding the runner profile,
credential, workspace snapshots, native sessions, and raw trace. The client
could retain flow definitions and UI metadata but must not launch Codex or
store native sessions locally. The existing bridge proves only a final-response
call through the Codex Python SDK using the user's default profile. The
app-server documents streamed items, tool calls, results, and thread
persistence. The credentialed probes must measure that gap in this runner
version; it is not yet an observed improvement over the bridge.

## Go/no-go

**No-go pending evidence.** Local tests verified fail-closed pair validation,
private no-model discovery, completed-item result classification, and
missing-snapshot refusal. No credentialed turns were made and no provider
spend was incurred. Conditions 1, 2, 3, 4, and 5 still need their indicated
credentialed observations before the proposed local MVP can pass all five.
