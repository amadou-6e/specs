# Native skill bundle discovery: initial findings

Status: partial evidence for issue #119, updated 2026-09-29. This publishes
discovery, manifest, and private-login test findings for #120 and #121. One
turn with both skill-selection inputs completed. This is not an implementation
decision.

The [Skill Revision](../components/skill-revision.md) proposal defines the
bundle contract; [shared contracts](../components/contracts.md) define
`SkillSnapshotRef`. The sanitized no-model
[Codex probe at commit `07a7d8d`](https://github.com/amadou-6e/laomedo/tree/07a7d8d/experiments/feasibility/119)
is the reproduction source for the local observations below; the experiment
is open for review in [Laomedo PR #1](https://github.com/amadou-6e/laomedo/pull/1).

## Bundled-script permission matrix

These are required grants to test, not permissions proven safe by this probe.
The [Codex sandbox reference](https://learn.chatgpt.com/docs/agent-approvals-security)
describes command, write, and network controls. The
[Claude skill guide](https://code.claude.com/docs/en/skills) describes
`${CLAUDE_SKILL_DIR}` and `allowed-tools` for bundled scripts.

| Operation | Codex | Claude | Laomedo boundary to verify |
| --- | --- | --- | --- |
| Discover `SKILL.md` metadata | Read materialized skill root; no script execution needed | Read materialized project `.claude/skills` root with `setting_sources=["project"]`; no script execution needed | Expose only the selected frozen bundle in the isolated project. |
| Read a rule, example, or reference | Agent file read must be allowed by sandbox | Read tool or equivalent file access | A selection list alone does not hide other files. Materialize only the selected dependency closure for subset mode. |
| Run a bundled script | Command execution under sandbox and approval policy | Bash permission; skill `allowed-tools` may pre-approve a command for the invocation turn | Treat script execution as a separate grant. Review script contents, interpreter, arguments, and inputs before a run. |
| Write scratch output | Needs a writable scratch root; read-only cannot satisfy scripts that write | Needs an allowed scratch path and write permission | Bind outputs to a disposable run directory, never a personal profile or canonical skill. |
| Network or external service | Separate network grant | Separate Bash/tool and network controls | Deny by default; record any explicit destination and credential mode. |

The Claude guide says `allowed-tools` grants permission during the invoked
turn and does not remove other available tools. A bundle's own frontmatter
can therefore expand execution permissions. It must be inspected before the
bundle is offered, not treated as an inert description.

## Item manifest pilot

An [overlay manifest pilot at `81ba239`](https://github.com/amadou-6e/laomedo/tree/81ba239/experiments/feasibility/119)
was tried read-only on two real skills with different
layouts. The `ui-design` bundle contains `SKILL.md`, two scripts, and agent
metadata (4 files). The `html-to-drawio` bundle contains `SKILL.md`, scripts,
and references (14 files). Their committed sample snapshots hold only
relative paths, per-file hashes, a canonical tree hash, stable item IDs,
source headings, item-content hashes, and a selection record. They do not
copy the source instructions. Regenerating both snapshots from the same
source checkout produced identical JSON and tree hashes.

The selected `ui-design` rule depends on `SKILL.md` and one inspector script;
the selected `html-to-drawio` usage example depends on `SKILL.md` and three
scripts. In both cases, native loading of the original `SKILL.md` exposes
other sections too. Thus a file-level dependency closure is not a truthful
isolated subset when multiple items share `SKILL.md`. The first
`SkillSnapshotRef` should identify the immutable full tree, selected item IDs,
item hashes, and dependency-file hashes separately. It should label these
pilots `direct_context_required` until a subset materializer can create a
new frozen skill file or the selected text is passed as direct context. This
is a recommendation from the pilot, not a proven native-selection behavior.

## Credential reuse without repeated sign-in

Authentication should belong to the runner, not to each disposable test
workspace or session. Provision one dedicated credential per provider in a
secret store, then let each test reuse it while receiving fresh profile,
workspace, and skill-materialization boundaries. Do not copy the current
interactive Codex or Claude profile into a test profile.

For Codex, an OpenAI project API key is the broadly available automation
path; the [Codex automation guide](https://learn.chatgpt.com/docs/non-interactive-mode)
recommends API keys for repeatable jobs and warns against exposing them to
repository-controlled scripts. Where an eligible ChatGPT workspace exists,
a [service-account access token](https://learn.chatgpt.com/docs/enterprise/service-accounts)
can represent a dedicated non-human identity without browser sign-in on each
run. The runner must keep the credential out of the materialized skill and
script environment; the exact broker or proxy boundary needs a #120 test.

For Claude Agent SDK use, Anthropic states that third-party developers
cannot offer claude.ai login or subscription rate limits without prior
approval; use [API-key authentication](https://code.claude.com/docs/en/agent-sdk/overview)
instead. `ANTHROPIC_API_KEY` takes precedence over subscription login when
present ([environment variables](https://code.claude.com/docs/en/env-vars)).
Keep Claude's private `CLAUDE_CONFIG_DIR` and session history separate from
the credential store. [Hosting guidance](https://code.claude.com/docs/en/agent-sdk/hosting)
supports persistent session storage or an external session store without
requiring a new login for every test.

This plan needs one credential-provisioning step per provider, not one login
per test. For this local spike only, [#119](https://github.com/amadou-6e/specs/issues/119)
permitted a one-time handoff of existing file-backed Codex ChatGPT auth into
a private runner auth store. The runner must not share the live personal
`CODEX_HOME` or copy personal settings, skills, plugins, or sessions. A
keyring-backed login is not covered. This exception does not extend to #120
or #121, and [#129](https://github.com/amadou-6e/specs/issues/129) owns the
later production authentication design.

The local handoff was attempted on 2026-09-28. A file-backed Codex ChatGPT
auth file was copied into an ignored, access-restricted private runner
directory inside the AGENTVIZ Git working tree. A constructed child
environment set private `HOME`, `USERPROFILE`, and `CODEX_HOME`; `codex login
status` reported ChatGPT login rather than API-key mode. This check alone does
not prove that the service accepted the copied credential for a model request.
The ignored directory was still inside a Git working tree, contrary to the
probe's stated location requirement. The sanitized
[probe source](https://github.com/amadou-6e/laomedo/pull/1) is in Laomedo PR #1.

The preflight listed the synthetic skill, six other private-state skill paths,
and no skill path outside the private state directory. The app-server listed
`gpt-6-luna` with low effort available. Two low-effort model turns submitted
both a `$skill` text mention and a structured `skill` input in the calling
agent's network-restricted tool context. This was not a restriction imposed
by the Codex thread's `read-only` sandbox. Neither emitted an agent message or
`turn/completed` within 90 seconds. The
instrumented second attempt reported `error` and `warning` notifications;
its private stderr had network and HTTP Forbidden signals. A credential-free
HTTPS check in that context could not connect to `chatgpt.com`, whereas a
network-enabled check received HTTP 200. The copied credential was not the
sole explanation for the stalled turns. The reproducible probe now checks
credential-free TCP reachability to `chatgpt.com:443` before any model turn;
its no-model preflight reports false in the restricted context and true in
the network-enabled context. This is a prerequisite check, not a guarantee
of authenticated request success.

The network-enabled command context could not access the first private
runner's ACL, so a second ignored, access-restricted private runner directory
was created inside the AGENTVIZ Git working tree. Only file-backed auth was
copied from the personal source. This was a second copy, beyond #119's
one-time handoff allowance. Both auth copies were deleted on 2026-09-29 after
review; no further model turns require them. The possibility of refresh-token
rotation affecting the personal login was not tested. The probe and auth check
now reject any `--state-dir` inside a Git working tree or Git metadata.
No-model login and discovery checks passed. The third and final permitted
`gpt-6-luna` low-effort turn completed in about eight seconds and returned
the exact marker from the selected synthetic skill. The private raw trace has
one assistant message with that marker, one usage event, and no tool calls.
It recorded 16,253 input tokens, of which 11,008 were cached, and 13 output
tokens. Applying the [GPT-6 Luna Standard short-context API
rates](https://developers.openai.com/api/docs/models/gpt-6-luna) gives about
**USD 0.00064 API-equivalent usage** for the completed turn, assuming Standard
processing. This is not an actual ChatGPT subscription charge. The first two
turns returned no usage, so their API-equivalent usage is unknown. All
**three submitted turns** under #119's cap have been used.

Corrected before/after comparisons for the successful third turn found the
personal skill roots, session root, and auth file unchanged. The first two
turns' session comparison was confounded by the concurrent IDE session. Their
auth-file comparison had a probe bug that hashed a file as a directory;
the probe now hashes files directly. The source auth hash was checked
separately during each handoff and was unchanged by those copies. The
successful marker shows the skill's instruction reached the model, but the
stream does not show a distinct skill-file read event. Because the turn used
the `$skill` text mention and structured `skill` input together while the
project root also made the skill discoverable, this result cannot establish
which mechanism selected it. Isolated rule or example selection is also not
proven. A future authorized experiment should test structured `skill` input
alone; #119's three-turn cap is exhausted.

## Remaining experiments and blocker

- No dedicated Laomedo project/service credential is available. The local
  file-backed Codex handoff worked for one network-enabled model turn. This
  only tests local feasibility, not the production auth design in #129.
  Claude still requires a separate supported credential. Bundled-script
  execution, trace completeness, and selected-subset leakage remain
  unobserved. Do not make more #119 model calls under the three-turn cap.
- The installed Codex CLI disagrees with current user-root documentation.
  Pin a target CLI/SDK pair and repeat the no-model probe before #120 uses
  its discovery results.
- Test Claude `setting_sources=[]` and `["project"]` with decoy personal and
  project roots, then compare `system/init`, direct `/name` dispatch, and
  file-read behavior under an isolated credential.
- Expand the manifest pilot to item sources outside `SKILL.md`, changed
  headings, missing dependencies, and malicious symlink/path cases. The
  current samples do not prove those cases in either native runtime.
- Compare a full bundle with a materialized subset. If the subset enters as
  direct prompt context, record that mode and do not call it native discovery.
