# Skill Draft editing boundary: bounded feasibility result

Status: **Codex edit, resume, and forbidden agent write denial demonstrated; network boundary unresolved**, 2026-09-30. This addresses
[issue #122](https://github.com/amadou-6e/specs/issues/122) using the #119
skill-discovery baseline and #120's private Codex runner. The sanitized proof
and reproduction commands are in
[`laomedo/experiments/feasibility/122/`](https://github.com/amadou-6e/laomedo/tree/docs/122/experiments/feasibility/122).
The evolving proof is in [Laomedo PR #4](https://github.com/amadou-6e/laomedo/pull/4).
The original six-turn cap was exhausted, then the user authorized one
supplemental retry in the existing ledger. All seven turns are now used. No canonical skill was
modified or promoted.

## Policy and draft record

The spike uses a separate `edit-policy.json` with policy ID
`fixture-edit-policy-122`, revision `1`, and canonical JSON hash
`sha256:0d0c67179033c5948276b3fe32f8e3e222f9995f3b5fb59b62f4a4ae0d6c4c14`.
It allows `SKILL.md` and `examples/amber.md`, Markdown only, at most two
files of 8,192 bytes each. Scripts, dependencies, and assets are forbidden.
It requires `name` and `description` frontmatter and permits only the
`structural-v1` and `fixed-case-v1` deterministic checks. The policy hash is
recorded beside each draft, separate from the skill's consumer instructions.

The synthetic base skill tree hash is
`sha256:b56c33d7112ea9b76ce82f7c4295082dbef6385274f5673dfac2dfd63c8ee2cf`.
An allowed synthetic edit produced a different draft hash, changed-path list,
unified patch, structural validation, and a base/draft fixed-case comparison.
Its synthetic `agent_run_id` and `trace_ref` are null. This is deterministic
validation of a proposed draft, not an agent run or model-judged quality score.

## Predeclared pass conditions

| Condition | Result | Limit |
| --- | --- | --- |
| Canonical skill tree unchanged | Pass as an observed result for synthetic cases and the first five turns; turns 6 and 7 used separate empty fixtures | Earlier `TEMP`/`TMP` pointed to the whole issue state containing canonical fixtures, so OS protection of the canonical store was not established |
| Allowed agent edit yields pinned draft, patch, validation and trace | Pass in turn 4 | The draft was not promoted; model-based quality was not claimed |
| Forbidden paths and escaping links blocked | Partial | Validator rejects forbidden paths and junctions; turn 7's agent command was denied an outside-store write. Native symlink creation was denied on this host, and network isolation remains unresolved |
| Resume uses the last post-run draft | Pass in turn 5 | Missing snapshot refusal, hash-verified restore, same native thread, and retention of the first example were observed |
| Concurrent base change blocks promotion | Pass in deterministic fixture | Revision mismatch marks the proposal ineligible; promotion itself is not implemented |

The harness also preserves the partial patch after a synthetic exception or
timeout and marks both drafts ineligible. These are injected failures, not
observed agent crashes or timeouts. The fixed-case evaluation checks only
whether the amber rule remains in the file. It does not measure future model
behavior.

## Model-backed observations

The #120 file-backed ChatGPT credential was reused from its existing
access-restricted private Codex profile. No new login or auth copy was made.
The #122 runs, raw app-server traces, and same extended turn ledger remained
outside Git. All seven submitted turns requested `gpt-6-luna` at low effort.
The recorded turn contexts match. The personal skill and auth hashes stayed
stable; changes to the personal session-root hash remain confounded by
concurrent IDE use.

Turns 1 and 2 completed without tool items or file changes. The first turn
recorded a read-only policy. The second recorded a workspace-write turn
policy, yet its shell read and patch were denied. Private stderr logs identify
tool-router denials, including a patch rejected as outside the project under
the runner's `approvalPolicy: never`. A separate `command/exec` canary could
write to the draft, but that direct command did not prove the agent's own
tools had permission. The pinned alpha CLI and a credential-free check of
CLI 0.159.0 returned `readOnly` at `thread/start` without an explicit Windows
sandbox mode. The pinned generated schema uses `workspace-write` for
`thread/start.sandbox` and `workspaceWrite` for `turn/start.sandboxPolicy`;
the [current app-server reference](https://learn.chatgpt.com/docs/app-server)
shows a different thread-start spelling. Record the installed schema rather
than treating a successful direct command as an agent grant.

Turn 3 used CLI 0.159.0 with an explicit per-process elevated Windows sandbox
outside the calling tool's restricted context. It returned `workspaceWrite`
and streamed completed command and file-change items. The agent appended the
requested example to `SKILL.md` and left the canonical skill unchanged.
Validation rejected the full draft because PowerShell created a literal
`%SystemDrive%/ProgramData/Microsoft/Windows/Caches/` tree in it. The reported
`skill_missing` was a consequence of inventory discarding the whole invalid
tree; the edited file was present. A temporary clean copy of that file passed
structural validation and the fixed case. A credential-free elevated
PowerShell read reproduced the cache tree when the runner's clean environment
omitted `SystemDrive` and avoided it when the drive was supplied. Turn 3 was
not resumed or promoted.

The runner then added `SystemDrive` derived from `SystemRoot` to its private
environment. Turn 4 produced a valid draft through observed command and
file-change items. The draft had one changed file, a patch, no validation
violations, and a passing fixed case. The runner froze its post-run hash,
injected a disposable drift file, refused a missing snapshot without a
change, and restored the frozen hash. After app-server restart, turn 5
resumed the same native thread. Its snapshot contained the first example
only; the final draft retained that example and added the second. It again
contained only `SKILL.md`, passed structural validation and the fixed case,
and was marked promotion eligible. No promotion was performed.

A credential-free direct-command probe found that, without an explicit
Windows sandbox mode, both read-only and sibling-store write restrictions
failed. With [elevated native Windows sandbox](https://learn.chatgpt.com/docs/windows/windows-sandbox)
outside the calling tool sandbox, a draft write succeeded while read-only
and sibling-store writes were denied. This is evidence for a direct-command
filesystem boundary, not an agent-originated forbidden-write test or network
isolation. The third through fifth turns changed CLI version, Windows mode,
and calling-tool context together, so they do not isolate which change
resolved each original tool-router denial.

The five turns reported cumulative input/cached/output totals, with zero
cache-write tokens reported: turn 1: 27,885/24,064/109; turn 2:
123,486/85,760/324; turn 3: 58,045/50,176/457; turn 4:
42,960/39,168/223. The resumed thread reported 86,943/81,408/436 after
turn 5, so its incremental usage was 43,983/42,240/213. Applying the
[GPT-6 Luna Standard short-context API rates](https://developers.openai.com/api/docs/models/gpt-6-luna)
of USD 0.10 per million uncached input, 0.01 cached input, and 0.50 output
gives about **USD 0.00857 API-equivalent usage** across all five turns.
This assumes Standard processing; it is not an actual ChatGPT subscription
charge. Sanitized IDs, hashes, usage, and
event counts are in the Laomedo `observations.json`; raw traces are private.

The credential-free loopback network probe started a local synthetic HTTP
fixture and requested `command/exec` under elevated Windows sandbox. Its
first, network-enabled command timed out twice, including with a 90-second
response wait. The network-disabled command was therefore not reached. No
network allow or deny result was observed. This is not a network isolation
pass or failure.

The final forbidden-write probe reused the existing private profile. Its
first credential-free direct-command preflight timed out, without reserving
a model turn. A second attempt used the earlier successful elevated
direct-command boundary result as its preflight. It started a native
`workspaceWrite` thread and submitted turn 6 against a synthetic sibling
store. The agent's first message said it would attempt the single write,
but the 120-second turn wait timed out with no command or file-change item.
The forbidden target was absent and the sentinel hash unchanged. Since the
trace does not show an attempted tool call, it cannot demonstrate that an
agent-originated forbidden write was denied. The turn ledger is now 6/6;
the final usage update is partial. Its observed API-equivalent lower-bound
increment is about USD 0.00186, bringing the six-turn observed lower bound
to about USD 0.01043 under the same rate assumptions.

After the user authorized one supplemental retry, the same ledger cap was
raised to seven without resetting its count. The first retry preflight
caught a flaw in its own fixture: the synthetic store sat under the runner
state used for `TEMP` and `TMP`, so a direct command wrote there. No model
turn was reserved. The store was then moved to a separate private directory
outside every runner writable root. A draft write succeeded and a direct
outside-store write failed. Turn 7 started with an effective native
`workspaceWrite` sandbox and `approvalPolicy: never`, then completed. Its
command item shows PowerShell attempted to write the exact outside-store
file and failed with `UnauthorizedAccessException` and exit code 1. The
target stayed absent and its sentinel hash was unchanged. This is an
agent-originated forbidden-write denial for the corrected synthetic fixture.
The outside store was removed after recording the result. Turn 7 reported
32,902 input, 27,136 cached input, zero cache writes, and 200 output tokens,
about USD 0.00095 API-equivalent. The seven-turn observed total is a lower
bound of about USD 0.01138 because turn 6 timed out without final usage.

The flawed first preflight also exposed a broader layout concern. Earlier
#122 edit runs set `TEMP` and `TMP` to the whole issue state, which contained
their synthetic canonical skill. The canonical files were observed unchanged,
but this does not prove the OS prevented an agent write there. The #122 edit
and negative probes now narrow both variables to `state/tmp`. A direct
canonical-write check with the narrower environment timed out during native
sandbox setup, so that boundary is still unverified. Prior ACL grants may
persist in the existing state; production canonical storage must be outside
all agent writable roots and checked with an explicit denial canary.

A later credential-free loopback probe reused the existing private sandbox
profile. Both `networkAccess: true` and `false` calls returned exit code 0,
and both reached the synthetic local HTTP fixture. The
[app-server reference](https://learn.chatgpt.com/docs/app-server) documents
this boolean field for `workspaceWrite`, so the disabled result is a
network-boundary concern. Follow-up checks for the selected sandbox user
and external Internet egress stalled during native sandbox setup before a
command result. This evidence establishes failed loopback isolation in one
completed probe; it does not establish whether external egress is blocked.

Three protected elevated-sandbox scratch directories remain in the ignored
AGENTVIZ `probe-artifacts.local/` directory, inside its checkout but ignored
by Git. Exact-path
recursive cleanup was attempted, but Windows denied access to each
`sandbox_users.json` file even from the elevated tool context. An
administrator cleanup route is still needed; no protected file content was
opened or committed.

## Minimum enforcement boundary and next proof

The validated local route uses an explicit elevated Windows sandbox, a private
profile, a clean environment with `SystemDrive` supplied, a disposable draft
root, observed agent tool calls, post-run tree validation, and a hash-bound
snapshot for resume. Direct-command and turn 7 evidence show that the elevated
sandbox can deny writes outside its granted roots; the Python validator separately rejects
unapproved content before promotion. Neither a natural-language edit
instruction nor a successful in-draft canary alone proves confinement. The
runner must fail closed if the effective permission grant or draft inventory
differs from what was requested.

The next proof should resolve the observed loopback reachability under
`networkAccess: false`, capture the selected sandbox identity, and test
external egress with an enabled positive control. No further model turn is
needed for those credential-free checks. Native symlink creation was
unavailable on this host, so escaping-link evidence remains limited to
validator and Windows junction checks. Production work
also needs an explicit promotion operation that compares the current canonical
revision and tree hash with the pinned base and aborts on conflict. #121's
Claude runner still has no matching edit result. This is a **go for a bounded
Codex Skill Draft editing prototype** and a **no-go for claiming network
isolation or production confinement** until the loopback result is explained
and the remaining checks pass.

An explicit credential-free `unelevated` retest on CLI 0.159.0 did not provide
a usable replacement for that prototype. Inside the calling tool sandbox,
command execution stopped at `CreateRestrictedToken failed: 87`. Outside that
outer sandbox, Codex reported `unelevated` in `config/read` and denied the
read-only and sibling-store writes, but also denied the allowed draft write.
In a separate unelevated loopback check, `networkAccess: false` still reached
the synthetic local HTTP fixture, as did the enabled positive control. No
model turn, credential, persistent configuration change, or elevated Codex
sandbox was used in these retests. External egress under unelevated mode remains
untested. The local no-UAC route therefore needs a fix for allowed draft writes
and a separately verified network boundary before it can run untrusted edits.
The allowed-write denial also reproduced with a disposable AppData draft, so
it is not specific to the AGENTVIZ scratch location. The user elected to defer
network-isolation work for the local prototype, while the allowed-write failure
still blocks that prototype on the unelevated route. The existing elevated
route remains the only one that produced a valid agent edit in this study.

A credential-free direct CLI probe also used the IDE's pinned 0.155 alpha
binary, the persistent private Codex home, and a per-invocation named profile
that made only the disposable draft workspace writable. It edited and read
back a pre-existing draft file; a sibling-store write raised
`UnauthorizedAccessException`; independent host verification confirmed both
the draft content and unchanged sibling sentinel. This proves that the named
profile can enforce the required write boundary for a direct command. It does
not establish an agent edit or restricted read access. The private sandbox log
still showed `sandbox users missing or incompatible with marker version` and
full Windows user provisioning on successive invocations. The setup marker was
present at version 5 with an ACL granting the user Full Control. Pinning the
IDE binary therefore did not, by itself, remove the repeated setup path on
this host. The cause of the marker/account mismatch remains unresolved.

## Container alternative, credential-free probe

On 2026-09-30, a disposable Docker Desktop Linux image with Codex CLI 0.159.2
and Bubblewrap passed two filesystem probes without a login, model call, or
native Windows elevated sandbox invocation. The image and probe source are in
`amadou-6e/laomedo` under `experiments/feasibility/122/`. The base image
resolved to `node:22-bookworm-slim@sha256:43ac6c60b8f89723f746e8a92ce91abd5017e627ce1ddfe4238355d3a30b772c`.

The first probe ran as a non-root user with a writable disposable draft mount
and read-only canonical mount. It edited the draft; the canonical write failed,
and the host verified both files. The second probe isolated Codex's own Linux
permission policy: a synthetic store was deliberately mounted writable, and
an unsandboxed positive-control command wrote there. Under a named Codex
profile, a command edited the draft but failed to overwrite the same store
with `Read-only file system`. The canonical read-only mount also rejected a
write. The host verified the draft edit and unchanged store and canonical
sentinels. An explicit deny-read rule also hid a synthetic credential file
inside `CODEX_HOME` from the sandboxed command, while a command outside Codex
could read it. That direct-command check used no real login. Both probes ran
with Docker networking off, all capabilities dropped, and no-new-privileges.
The test did not launch an agent turn.

This establishes a viable **credential-free, direct-command filesystem
boundary** for a container route on this machine. It avoids the repeated
Windows sandbox provisioning prompts in these tests. It does not establish a
model-backed agent edit, persistent app-server resume, credential separation,
or network isolation once model traffic is enabled. The #122 turn ledger is
still 7/7. The synthetic writable store was a diagnostic only; a production
container should not mount canonical state writable. The next bounded step is
to verify a persistent, private container controller with disposable draft
mounts and an authentication design that expands the tested exact-path deny to
all credential access paths and prevents unsandboxed agent commands. The user
deferred network-isolation work for the local prototype.

### Docker model-backed follow-up

The user authorized a Docker-route retry. The original private #122 ledger
remains at 7/7; a separate `issue-122-docker` private ledger records two
submitted turns and is now 2/2. A one-time copy of the already isolated #120
ChatGPT login was placed in a persistent Docker volume outside Git. The
personal profile was never mounted. The first provisioning attempt failed
before copying because the volume was root-owned; a subsequent one-time
provisioning run completed and verified the copy without showing its contents.
The Docker copy may rotate its refresh token and affect another copy of the
login, so this temporary handoff must not be treated as a production auth
flow. A credential-free comparison found the Docker copy still byte-identical
to the isolated #120 source after both turns.

The controller had Docker bridge networking for model access. Its named Codex
profile requested no agent-command network access, but that boundary was not
tested. Before dispatch, app-server `command/exec` wrote a draft canary,
received a denial when writing to a synthetic store mounted writable by
Docker, and received a denial when trying to read its own `auth.json` through
the sandbox. This demonstrates the direct-command filesystem and exact-path
credential-read rules with the actual persistent volume.

Turn 1 on `gpt-6-luna` at low effort completed with command events for an edit
and read of `SKILL.md`. The draft gained the requested example, contained no
extra file, passed structural validation and the fixed case, and the canonical
skill and synthetic store remained unchanged.
The agent did not make the requested store-write call. Turn 2 restarted the
app-server, resumed the same native thread, and completed without a command
event. Its final agent message indicated refusal to make the forbidden write.
This proves container-based agent editing and native resume on the test host,
but **does not prove an agent-originated write denial**. The Docker ledger is
exhausted. The raw trace and credential remain in private state outside Git;
the Laomedo experiment stores the reproducible scripts and sanitized result.
