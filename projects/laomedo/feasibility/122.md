# Skill Draft editing boundary: bounded feasibility result

Status: **no-go on current evidence**, 2026-09-29. This addresses
[issue #122](https://github.com/amadou-6e/specs/issues/122) using the #119
skill-discovery baseline and #120's private Codex runner. The sanitized proof
and reproduction commands are in
[`laomedo/experiments/feasibility/122/`](https://github.com/amadou-6e/laomedo/tree/docs/122/experiments/feasibility/122).
Two of the permitted six Codex turns were submitted. No canonical skill was
modified or promoted.

## Policy and draft record

The spike uses a separate `edit-policy.json` with policy ID
`fixture-edit-policy-122`, revision `1`, and canonical JSON hash
`sha256:0d0c67179033c5948276b3fe32f8e3e222f9995f3b5fb59b62f4a4ae0d6c4c14`.
It allows `SKILL.md` and `examples/amber.md`, Markdown only, at most two
files of 8,192 bytes each. Scripts, dependencies, and assets are forbidden.
It requires `name` and `description` frontmatter and permits only the
`structural-v1` and `fixed-case-v1` deterministic checks. The policy hash is
recorded beside each draft, separate from the skill's consumer instructions.

The synthetic base skill tree hash is
`sha256:b56c33d7112ea9b76ce82f7c4295082dbef6385274f5673dfac2dfd63c8ee2cf`.
An allowed synthetic edit produced a different draft hash, changed-path list,
unified patch, structural validation, and a base/draft fixed-case comparison.
Its synthetic `agent_run_id` and `trace_ref` are null. This is deterministic
validation of a proposed draft, not an agent run or model-judged quality score.

## Predeclared pass conditions

| Condition | Result | Limit |
| --- | --- | --- |
| Canonical skill tree unchanged | Pass for all synthetic cases and both Codex turns | The personal session-root comparison remains confounded by concurrent IDE use |
| Allowed agent edit yields pinned draft, patch, validation and trace | **Fail to demonstrate** | Synthetic edit has those draft artifacts but no agent trace; both Codex turns changed no file |
| Forbidden paths and escaping links blocked | Partial | Post-edit validator rejects forbidden paths and Windows junctions; native symlink creation was denied on this host; no OS write prevention was demonstrated |
| Resume uses the last post-run draft | Partial | Deterministic snapshot restore and missing-snapshot refusal pass; no valid agent edit existed to resume |
| Concurrent base change blocks promotion | Pass in deterministic fixture | Revision mismatch marks the proposal ineligible; promotion itself is not implemented |

The harness also preserves the partial patch after a synthetic exception or
timeout and marks both drafts ineligible. These are injected failures, not
observed agent crashes or timeouts. The fixed-case evaluation checks only
whether the amber rule remains in the file. It does not measure future model
behavior.

## Model-backed observations

The #120 file-backed ChatGPT credential was reused from its existing
access-restricted private Codex profile. No new login or auth copy was made.
A distinct #122 workspace and six-turn ledger were created beneath that
private root, outside Git. Both submitted turns requested `gpt-6-luna` and
`low`; the matching private `turn_context` recorded those settings. Both
threads completed, but the draft bytes matched the base and their event
streams contained only user/agent messages, with no tool item, file change,
or matching call/result pair.

The first probe requested `workspace-write` on `thread/start`. This pinned
CLI returned an effective `readOnly` thread policy. The second probe used
the pinned CLI's `workspace-write` thread enum and added a turn-level
`workspaceWrite` policy. A credential-free `command/exec` canary wrote inside
the disposable draft directory under that policy, but `thread/start` still
reported `readOnly`. Inspection of the second private turn's `turn_context`
record showed `sandbox_policy.type: workspace-write`; the first turn recorded
`read-only`. Despite that second turn policy, the agent's synthetic response
reported that its shell read and patch write were blocked by environment
policy. The stream contained no tool item. The canary and turn context prove
that the requested policy reached two different protocol surfaces; neither
proves the agent had a usable edit tool.

This distinguishes four surfaces that must not be conflated: a requested
thread mode, the returned thread policy, the recorded turn policy, and a
command run with an explicit policy. The [current official app-server reference](https://learn.chatgpt.com/docs/app-server)
shows `workspaceWrite` for `thread/start`; the pinned CLI's generated schema
instead accepts `workspace-write` there and `workspaceWrite` in
`turn/start.sandboxPolicy`. The probe records this version-specific mismatch
and refuses to claim usable agent editing from a successful canary alone.
A separate credential-free check of official Codex CLI 0.159.0 returned the
same `readOnly` thread policy while its explicit `command/exec` canary wrote
successfully. Changing the binary alone did not resolve this host's agent-tool
blocker; no model turn was submitted with 0.159.0.

The personal skill and auth hashes were stable. The personal sessions hash
changed while an IDE Codex session was active, so the personal-session
boundary remains inconclusive, as in #120. The private raw app-server streams
were inspected locally and not committed. Sanitized native IDs, usage,
call counts, and event counts are in the Laomedo `observations.json`.

The two fresh threads reported final cumulative totals of 27,885 input /
24,064 cached / 109 output tokens and 123,486 input / 85,760 cached / 324
output tokens, with zero cache-write tokens. Applying #120's recorded GPT-6
Luna Standard short-context rates to uncached input, cached input, and output
gives about **USD 0.00547 API-equivalent usage**. This is not an actual
ChatGPT subscription charge. Two turns are consumed; four remain under the
issue cap. No further turn should be spent on the same unverified write setup.

## Minimum enforcement boundary and next proof

The current Python validator can reject a changed file before a proposal is
promoted, but it cannot stop the agent from first writing outside the draft.
The minimum viable boundary therefore needs an OS-enforced writable root
limited to the disposable draft, a private profile, a runner-side policy check
before dispatch, and post-run tree validation. Resolve links and Windows
junctions without traversing them. Snapshot the complete post-run draft, bind
its hash to the native session, and refuse resume before any workspace
modification when the snapshot is unavailable. A separate promotion operation
must compare the current canonical revision and hash with the pinned base and
abort on conflict.

The next bounded test should first demonstrate an agent tool call and matching
result in a disposable workspace, then perform an allowed edit and
resume from its post-run snapshot. Only after that should it test an attempted
forbidden write against the OS boundary. Do not spend the remaining turns on
prompt-only path restrictions. #121's Claude runner remains blocked by its
missing native CLI and dedicated credential, so no Claude edit result is
claimed here.
