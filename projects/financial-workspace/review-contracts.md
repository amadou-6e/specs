## Recurring service and schedule history

A recurring service has stable `service_id`, provider, contract/evidence IDs, billing frequency, expected amount/currency, effective date range, and current subscription status. A separate `service_month` record captures each planned or observed month, including zero-value `Not active` months. Its stable key is `service_id + YYYY-MM`; keep the existing Notion page ID and original CSV row identity where available. An observed charge can link one service month to one or more posted transaction IDs; a posted transaction may cover multiple service months or services only with an explicit allocation. The sum of allocations cannot exceed the posted movement in its currency.

`recurring-expenses.csv` is a migration input, not a transaction file. Preserve all rows and their `Date`, `Service Month`, `Price`, `Payment date`, `Subscription Status`, and source fields. A zero-price or inactive row remains schedule history, never a zero-value cash movement. A positive expected price without a verified posted transaction is a forecast or open obligation, not actual cash flow. For example, the live Coursera row dated 2025-09-01 has `Price=0`, `Subscription Status=Not active`, and a reference saying no active subscription; it must remain visible in recurring history and contribute zero rows to Transactions. Use posted transactions, not the Recurring table's `Price`, for confirmed cash-flow totals.

The migration must compare recurring row counts by service and month, zero/inactive row counts, observed-charge links, and unlinked charged months. No recurring page is deleted or repurposed as a Transactions row. If a recurring charge was also filed in Procurement, retain both historical pages but mark them as two descriptions of one canonical transaction. The joined cash-flow view counts its transaction ID once.

## Liabilities, interest, and refundable deposits

A liability is a dated obligation balance with `liability_id`, creditor, principal, accrued interest, other charges, currency, as-of date, evidence, status, and settlement links. A balance snapshot is not a cash movement. The current KfW page records EUR 5,700 principal and EUR 779.45 accrued interest, total EUR 6,479.45, based on a statement dated 2026-08-03. Keep principal and interest as separate components, do not infer subsequent interest, and reconcile both against the Drive statement and later statements before changing the page. Loan disbursement and repayment are linked posted movements; repayment allocation reduces principal and/or pays interest according to provider evidence. Interest expense is recognized in the chosen reporting basis only once; a balance accrual is not itself a cash outflow.

The EUR 2,500 landlord deposit is currently a payable, with due date and payment source unverified in the live page. Before payment it is a liability/open matter, not a transaction or refundable asset funded by cash. On verified payment, record the one actual negative bank movement, link it to the deposit obligation, clear the payable by the settled amount, and recognize an equal refundable-deposit asset. Classify the movement as a deposit/asset transfer for consolidated cash-flow presentation, not rent or consumption. On return, record the positive movement and reduce the asset; any withheld amount becomes an expense only when supported by settlement evidence. Partial payment or return adjusts balances proportionally and keeps the matter open.

SSKM loan contract and disbursement evidence is already filed under Drive Liabilities. The liabilities register cannot be marked complete until the SSKM loan has been inventoried, its current balance and terms reconciled to dated evidence, and any missing statement periods or discrepancies logged in the central exception register. Until then the report must say `partial`, list the covered liabilities and as-of dates, and avoid claiming a complete net-worth snapshot.

## Migration of Git-tracked statement evidence

The current financial-workspace Git repository tracks original PDFs and extracted `.txt` files under `data/statements/2024`, `2025`, and `2026`; its per-year manifests already contain some Drive IDs. Do not delete or rewrite these files as the first step. Build `config/cashflow/sources.yaml` from the tracked manifests and a Drive inventory, with one stable source ID per exact file, Drive ID and current path, provider/account, coverage period, MIME type, byte size, local SHA-256, Drive revision or modification time when available, parser/extractor version, and permission-check result. Extracted text is a derived artifact with a `derived_from` source ID and its own hash, not a substitute for the PDF.

Compare every Git-tracked PDF byte hash with the corresponding Drive download. Investigate a mismatch as a distinct version; never silently replace a source. Verify the current user can fetch each indexed Drive ID on a fresh machine. Replay one closed month using only the pinned code revision, indexed Drive files, reviewed decisions, and documented credentials, then compare row IDs and totals to the existing run. Only after all covered files pass that gate may a separate PR stop tracking current PDFs/text and add ignore rules. Preserve existing Git history and old scripts for auditability; rewriting historical commits to purge sensitive data is a separate explicit decision because it changes clone semantics. Record old path to source ID to new cache path mappings and keep compatibility wrappers until downstream scripts pass against the new layout.

## Local Drive mirror cache

Use one top-level ignored `cache/` whose contents mirror the Drive `Financial Workspace/` path below it, for example `cache/Banking/SSKM/2023/SSKM_2023-01_Kontoauszug.pdf`. The path is a navigation convenience; `sources.yaml`'s Drive file ID and expected hash remain authoritative. The draft-only `drive-folder-example/Financial Workspace/` is not this cache and is not published in Git.

A known local path can be checked before a network call. In offline replay mode, accept it only if its hash matches the pinned source index and report that remote path/permission freshness was not checked. In online refresh mode, resolve the current Drive parent chain by file ID, compare it with the indexed and cached path, and move or re-fetch into the new mirrored path after verifying bytes. Never serve a stale old-path entry under the new name without validation. Same-name collisions receive a deterministic suffix derived from Drive file ID; native Docs need explicit export format and hash rules. Cache can be deleted and reconstructed at any time. `fetch` reports inaccessible, changed, or absent sources and records specific gaps in the exception register.

## Notion migration and joined Transactions view

Start with a read-only baseline of all three live data sources and the Cash Flow page. Store schemas, page IDs, property values, view IDs, row counts, and amount totals by status and currency. Build a migration crosswalk for each Procurement item, recurring month, and liability to canonical IDs. Do not change live pages during matching. Review ambiguous links and log them before write-back. Add relation/external-ID properties only after comparing a dry-run diff; preserve existing page IDs, fields, and views.

The authoritative `Transactions` source contains only posted account movements. Its `transaction_id` is unique per source account movement. A link table maps zero or more Procurement pages, Recurring service months, and Liabilities to each transaction, with explicit link type and allocation. A joined Notion view shows the transaction once and displays related pages through relations or rollups. It never concatenates Procurement `Price` and Recurring `Price` into another monetary fact. Totals are computed from unique verified transaction IDs, with owned-account transfer pairs excluded from income/expense and deposit movements shown separately. Verify that sum of allocations by transaction does not exceed its signed amount and that the same provider transaction does not create two canonical IDs.

Before switching the live Cash Flow page, compare row counts and sums by account, month, type, and currency against statement controls and the prior dashboard; explain differences caused by planned recurring rows, split orders, refunds, transfers, or exclusions. Publish a read-only preview on the existing page, keep its original linked views intact, and switch confirmed totals only after the crosswalk and reconciliation pass. Save the pre-change Notion export and rollback steps. A rollback restores the prior views and properties while retaining the canonical run and mapping for investigation.

## Tax-year workspaces and review artifacts

Use `Tax/<year>/` as a stable year ID; do not rename the folder whenever status changes. At the year root keep a small living `STATUS`, `DOCUMENT_ACQUISITION_CHECKLIST`, `EVIDENCE_MANIFEST`, and `NEXT_STEPS` set. They are working indexes, not original tax evidence. In Git they can remain Markdown; in Drive they can be native Google Docs linked to the repository documents or maintained as the chosen single editable copy. Define one authoritative location for each to prevent drift. The current local tax work uses `STATUS.md`, `DOCUMENT_ACQUISITION_CHECKLIST.md`, `EVIDENCE_MANIFEST.md`, and `NEXT_STEPS.md`; migrate their content and links without replacing them with a generic dashboard.

Subject folders such as `subjects/funding/`, `subjects/residence/`, `subjects/exchange/`, and `subjects/employment/` group analyses and links that cross income, deductions, and correspondence. Original evidence remains filed once in its natural Drive location and can be referenced by source ID from several subjects and tax years. Document-type folders such as `Filing/`, `Assessment/`, and `Correspondence/` are for original authority or submitted documents when useful; they are not the only organizing axis. A tax-year-to-source crosswalk records `tax_year`, `subject_id`, `source_id`, role, date range, and whether a fact is allocated to one or several years. Shared contracts and multi-year scholarship awards keep one original Drive file ID with multiple year links, never physical duplicates.

`review_artifacts/<review_id>/` holds external or self-review findings as immutable files with reviewer, review date, reviewed input commit/hash, scope, artifact hash, and findings status. The mutable computation being reviewed stays in its subject folder. When a computation changes, add a response or superseding computation and link it to the frozen review; never edit the review artifact to match the new answer. A stale working analysis must carry a clear status and reference to the review that made it stale.

Track each tax year as a Matter with `tax_year`, lifecycle status, last verified date, owner/next action, deadlines, and source coverage. The status must be visible on the Notion Matters table and in the year-root `STATUS`, with a periodic consistency check. Suggested statuses are `future`, `collecting`, `in preparation`, `filed`, `assessed`, `overdue`, and `closed`; `overdue` is a separate flag if a year is also in preparation. The review describes 2021 as closed, 2022 as overdue with a penalty, 2023 as in preparation, 2024-2025 as pending, and 2026 as future. Treat these as dated review observations, not automatically current statuses or authoritative tax calculations. Do not encode state in folder names, since it changes without changing the year identity.
